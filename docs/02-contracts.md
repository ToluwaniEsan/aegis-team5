# 02. Shared contracts

This file is the agreement between the three workstreams. Every message, state, command and screen field that crosses a workstream boundary is defined here. Build against it exactly.

**Frozen rule.** After Phase 0 these contracts are frozen. A change needs a pull request titled `CONTRACT CHANGE: ...` that edits this file, the Python models and the TypeScript types together, approved by all builders. Agents must never change a contract on their own to make their code work.

Sources of truth in code:
- Python messages: `backend/aegis/common/models.py` (pydantic v2 models for sections 2 to 4, 7 and 10). Owner: Zizwe.
- Python screen protocol: `backend/aegis/common/ui_models.py` (pydantic v2 models for section 9). Owner: Emmanuel.
- TypeScript: `frontend/src/contracts/ui.ts` (the UI protocol in section 9, copied exactly). Owner: Emmanuel.
- Settings: `config/config.yaml`

## 1. Conventions

- **Units:** metric only, in the field name: `mass_kg`, `shift_cm`, `energy_wh`, `speed_mps`, `latency_ms`, `eta_s`, `range_km`. Positions are `lat` and `lon` in decimal degrees (GEN-002).
- **Time:** UTC, ISO 8601 with milliseconds and a `Z`, for example `2026-11-19T15:04:05.123Z` (GEN-002).
- **IDs:**
  - Payload: `PAY-YYYY-NNN`, generated by the ground station at mission assignment (AEG-510).
  - Mission: `MSN-YYYY-NNN`.
  - Message: `msg_id` is a UUID4.
  - Fault: `fault_id` is a UUID4. The fault `code` is from the catalog in section 7.
- **Enums** are UPPER_SNAKE strings.
- **Clock:** no module reads the wall clock directly. Everything takes a `Clock` object (`RealClock` in production, `ManualClock` in tests) so timeouts can be tested without sleeping.

## 2. Message envelope

Every message between modules, processes and teams is one JSON object on one line.

```json
{
  "v": 1,
  "msg_id": "6f1c2a9e-1d3b-4c55-9a51-2f2a0f3b7c11",
  "type": "cmd.release",
  "iface": "I2",
  "src": "ground.command_manager",
  "dst": ["vehicle.payload_controller"],
  "sent_at": "2026-11-19T15:04:05.123Z",
  "priority": 2,
  "mission_id": "MSN-2026-007",
  "payload_id": "PAY-2026-007",
  "corr_id": null,
  "buffered": false,
  "body": {}
}
```

| Field | Rule |
|---|---|
| `v` | Always `1`. |
| `type` | `<domain>.<name>` from the catalog in section 3. |
| `iface` | `I1` to `I9` (Figure 1 and the PRD tab), or `INT` for messages inside one side. |
| `src` | One endpoint name from the table below. |
| `dst` | List of endpoint names. A command to the vehicle and Team 2 lists both. |
| `priority` | `0` emergency stop, `1` commands and acks, `2` status. The link always sends lower numbers first. |
| `corr_id` | On an `ack`, the `msg_id` of the command it answers. Otherwise `null`. |
| `buffered` | `true` when the Event Buffer replays a message that was held during a link outage. |

**Endpoints**

| Side | Endpoint | Owner |
|---|---|---|
| Ground | `ground.command_manager`, `ground.status_monitor`, `ground.alert_manager`, `ground.mission_log`, `ground.ui_server`, `ground.fault_injector` | Workstream B |
| Ground | `team1.integration` (stand-in, later adapter) | Workstream B |
| Link | `team3.link` (stand-in, later adapter) | Workstream B |
| Vehicle | `vehicle.payload_controller`, `vehicle.payload_simulator`, `vehicle.event_buffer`, `vehicle.link_watch`, `vehicle.test_agent` | Workstream A |
| Vehicle | `team2.nav`, `team4.power` (stand-ins, later adapters) | Workstream B builds them, A uses them |

## 4. Payload state machine (Workstream A owns it, everyone reads it)

States: `EMPTY`, `LOADED`, `SECURED`, `TRAVELLING`, `AT_DESTINATION`, `RELEASED`, `DELIVERED`, `RETURNING`, `HELD`.

`RETURNING` is not in the PRD state list but is in Figure 2. It is needed so that a payload heading home can never be released, and so that arriving home does not look like arriving at a destination.

**Two flags matter everywhere:**
- **`secured`** is true only when the lock is closed, every lock sensor is OK, the mass is settled and in range, and `shift_cm` is at or below `unsecured_shift_cm`. A shift over the limit makes the payload unsecured (AEG-502). That blocks release and departure even though the lock is still closed.
- **`departure_permitted`** is true only when **all three** hold: the state is SECURED, `secured` is true (which includes mass in range), and a mission is open. A payload that returned to the origin is SECURED with its mission closed, so departure stays blocked until it is unloaded and a new mission is assigned. This is the one definition; every other doc refers to it.

### Command checks, in this order, before any state row is looked at

1. **`cmd.estop` skips every check below.** It is never rejected for age, clock or state (OI-019).
2. **Future timestamp:** `sent_at` more than `clock_skew_warn_s` ahead of the vehicle clock → REJECTED `FUTURE_TIMESTAMP`, and raise `CLOCK_SKEW`.
3. **Stale command:** `sent_at` older than `command_max_age_s` → REJECTED `STALE_COMMAND`. This is the vehicle half of the two-sided timeout.
4. **HELD:** only `cmd.ack_fault` and `cmd.estop` are processed; anything else → REJECTED `PAYLOAD_HELD`.
5. **The row in the table below.** A command with no row for the current state → REJECTED `INVALID_STATE`.

**Release guards, checked in this order** (the first failure is the reason given):
1. Moving → `VEHICLE_MOVING`.
2. Not at the destination → `NOT_AT_DESTINATION`.
3. Not secured → `NOT_SECURED`.
4. Active CRITICAL fault → `CRITICAL_FAULT`.

The ground uses the same order in `permissions.py`, so the screen and the vehicle give the same reason.

### Transitions

| From | Event | Guard | To | Side effects |
|---|---|---|---|---|
| EMPTY, DELIVERED | `cmd.assign_mission` | mass and dims within limits | LOADED | `sim.command LOAD` with the declared mass; ack COMPLETED once SECURED |
| EMPTY, DELIVERED | `cmd.assign_mission` | out of limits | unchanged | REJECTED `OUT_OF_LIMITS` |
| LOADED | `sim.reading` with `settled = true` | mass in range, lock not yet requested | LOADED | `sim.command LOCK` once (`lock_requested = true`); send `payload.mass_report` |
| LOADED | `sim.reading` with `settled = true` and `locked = true` | `secured` | SECURED | interlock opens |
| LOADED | `sim.reading` with `settled = true` | mass out of range | LOADED | raise `WEIGHT_OUT_OF_RANGE`; no LOCK |
| LOADED, SECURED | `cmd.update_payload` | not moving, values within limits | unchanged | `sim.command LOAD` with the new mass. The lock stays closed and the simulator re-weighs within `reweigh_time_s`. New `payload.mass_report`; ack COMPLETED when settled (AEG-512) |
| SECURED | `nav.state moving = true` | `secured` | TRAVELLING | |
| EMPTY, LOADED | `nav.state moving = true` | | HELD | raise `DEPARTED_UNSECURED` (CRITICAL). It should never happen if Team 2 honors the interlock. |
| TRAVELLING | `nav.state at_destination = true, moving = false` | | AT_DESTINATION | start the pre-release wait timer if the link is LOST |
| AT_DESTINATION | `nav.state moving = true` | | TRAVELLING | the vehicle left again; release is blocked |
| AT_DESTINATION | `cmd.release` | release guards pass | RELEASED | `sim.command RELEASE` |
| AT_DESTINATION | pre-release wait elapses | `prerelease_authorized`, link still LOST, release guards pass | RELEASED | release without a command (AEG-507). The wait counts from the later of arrival and link loss, and restarts after a HELD exit. |
| AT_DESTINATION | link LOST | not `prerelease_authorized` | unchanged | stay secured until the link returns and a fresh `cmd.release` arrives (AEG-514) |
| RELEASED | `release_done = true` | | DELIVERED | send `payload.delivered` (through the Event Buffer if the link is down); ack COMPLETED for the release |
| RELEASED | no `release_done` within `release_time_s + release_grace_s` | | HELD | raise `RELEASE_FAILED` (CRITICAL) |
| HELD (from RELEASED) | `release_done = true` | | HELD | send `payload.delivered` now; set `held_from = DELIVERED`. The release timer is never restarted. |
| TRAVELLING, AT_DESTINATION | `cmd.abort` or `cmd.return_to_origin` | | RETURNING | mission marked ABORTED for abort; ack COMPLETED |
| RETURNING | `nav.state at_origin = true, moving = false` | | SECURED | mission closed. Clear `prerelease_authorized`. `departure_permitted` stays false until the payload is unloaded and a new mission is assigned. |
| LOADED, SECURED (before departure) | `cmd.abort` | | EMPTY | `sim.command UNLOAD`; mission ABORTED |
| SECURED (mission closed, at origin) | test action `payload/unload` (ground crew) | | EMPTY | `sim.command UNLOAD` |
| DELIVERED | `cmd.return_to_origin` | | unchanged | navigation only; ack COMPLETED |
| LOADED, SECURED, TRAVELLING | `cmd.change_destination` | | unchanged | record the new destination; ack COMPLETED |
| RETURNING | `cmd.abort` or `cmd.return_to_origin` | | unchanged | REJECTED `INVALID_STATE` ("Already returning to origin") |
| any state | `cmd.ack_fault` | the fault exists | unchanged, then run the HELD exit check | ack COMPLETED |
| any except HELD | `cmd.estop` | | HELD | raise `ESTOP_ACTIVE`; `held_from` = previous state |
| HELD | `cmd.estop` | | HELD | ack COMPLETED; raise `ESTOP_ACTIVE` again if it was cleared |
| any except HELD | a fault with `holds_payload = true` | | HELD | `held_from` = previous state |
| HELD | **HELD exit check**, run on every `cmd.ack_fault`, every `fault.cleared` and every tick | every holding fault is acknowledged and its condition has cleared | `held_from` | |

### Rules that apply in every state

- **Release only from AT_DESTINATION.** Release is blocked in every other state. Tests check this from every state.
- **The lock opens only through `RELEASE` or `UNLOAD`.** If the Payload Controller process dies, the simulator keeps its last lock state, so the payload stays secured (GEN-004).
- **Lock opening raises a fault.** `PAYLOAD_UNSECURED` is raised whenever the lock reports open outside a `RELEASE` or `UNLOAD` the controller itself commanded.
- **Shared clock:** the future-timestamp and stale-command checks rely on assumption A-17. All nodes share UTC within 0.5 s, either on the same host or synced with NTP.

## 5. Commands the operator can give

The ground backend decides what is allowed and sends the answer to the screen in `allowed` (section 9). The screen never works this out itself. The vehicle checks again on its side, so a bug on one side cannot cause an unsafe release.

| Command | Allowed when | Confirmation (OI-003) | Sent to |
|---|---|---|---|
| `assign_mission` | With an active mission: always; it joins the queue (OI-015). With no active mission: only when the payload is EMPTY or DELIVERED, otherwise "Unload the payload first". | No | Payload Controller, Team 2 (`nav.assign`) |
| `start_queued_mission` | No active mission, the queue is not empty, and the payload is EMPTY or DELIVERED. Never starts on its own. | Yes | Same as assign |
| `remove_queued_mission` | Mission is in the queue | No | Ground only |
| `abort` | Payload LOADED, SECURED (mission open), TRAVELLING or AT_DESTINATION | Yes | Payload Controller, Team 2 |
| `return_to_origin` | TRAVELLING, AT_DESTINATION or DELIVERED | Yes | Payload Controller, Team 2 |
| `change_destination` | Payload LOADED, SECURED (mission open) or TRAVELLING | Yes | Payload Controller, Team 2 |
| `update_payload` | LOADED or SECURED and the vehicle is not moving (A-16) | No | Payload Controller |
| `release` | AT_DESTINATION, stopped, secured, no active CRITICAL fault, link not LOST. Reasons follow the release guard order in section 4. | Yes | Payload Controller |
| `ack_fault` | An unacknowledged alert exists | No | Payload Controller, or ground only for ground-side alerts |
| `estop` | Always | **No** (OI-019) | Payload Controller, Team 2, Team 4 |

Every refusal carries a short reason the operator can read, such as "Vehicle is moving" or "Payload is held: acknowledge the fault first" (OI-004). A HELD payload allows only `ack_fault`, `estop` and queue edits.

**Command lifecycle on the ground** (OI-006, OI-009):
- One operator command can produce two envelopes (`assign_mission` sends `cmd.assign_mission` and `nav.assign`). Its `command_id` is the `msg_id` of the first envelope. The Command Manager maps every envelope `msg_id` of that command back to the `command_id`, and tracks each recipient's acks separately.
- `SENT` when the Command Manager publishes the command.
- `RECEIVED` on the first `ack` RECEIVED.
- `COMPLETED` when every recipient has acked COMPLETED.
- `FAILED` on any REJECTED (show the reason), or when no RECEIVED arrives within `timing.command_timeout_s` (reason "No confirmation in 5 s. Not resent.").
- `FAILED` also when RECEIVED arrived but COMPLETED did not within `timing.command_complete_timeout_s` (reason "Received but not completed in 60 s").
- A failed command is never resent automatically. The operator must issue it again.
- Every transition reaches the screen within 2 s.

## 6. Missions and the queue

- On assignment the ground generates `mission_id` and `payload_id` and shows the payload ID on the form before sending (AEG-510, OI-001).
- Mission status: `ASSIGNED` (sent, payload loading), `ACTIVE` (TRAVELLING onwards), `COMPLETE` (DELIVERED), `ABORTED`.
- The queue is FIFO. A queued mission starts only when the operator confirms it after the active mission is COMPLETE or ABORTED (OI-015).
- Team 1 gets `t1.mission_report` on every status change.

## 7. Fault catalog

The Alert Manager owns this table. Severity labels and shapes are fixed: CRITICAL ▲, WARNING ◆, CAUTION ● (OI-018).

| code | severity | raised by | raised when | recommended action shown to the operator | holds payload |
|---|---|---|---|---|---|
| `ESTOP_ACTIVE` | CRITICAL | vehicle | Emergency stop pressed | Check the vehicle is safe, then acknowledge to clear the stop | yes |
| `PAYLOAD_UNSECURED` | CRITICAL | vehicle | Lock reports open outside a RELEASE or UNLOAD the controller commanded | Stop the vehicle at the next safe point and inspect the payload | yes |
| `DEPARTED_UNSECURED` | CRITICAL | vehicle | Vehicle moves while the payload is not SECURED | Stop the vehicle now and secure the payload | yes |
| `RELEASE_FAILED` | CRITICAL | vehicle | Release did not finish in time | Do not move the vehicle. Inspect the release mechanism | yes |
| `LOCK_SENSOR_FAULT` | CRITICAL | vehicle | Lock sensor reports FAULT | Treat the payload as unsecured. Stop at the next safe point | yes |
| `DRIVETRAIN_FAULT` | CRITICAL | vehicle (from Team 4's local `power.status`, so it works with the link down) | `drivetrain_health = FAULT` | Stop the mission and contact Team 4 support | yes |
| `PAYLOAD_SHIFT` | WARNING | vehicle | `shift_cm` over `unsecured_shift_cm` (AEG-502). The payload is reported unsecured, which blocks release and departure. | Reduce speed and inspect the payload at the next stop | no |
| `WEIGHT_OUT_OF_RANGE` | WARNING | vehicle | Measured mass outside limits | Correct the load before departure | no |
| `LOAD_CELL_FAULT` | WARNING | vehicle | Load cell reports FAULT | Weight readings are unreliable. Verify the load manually | no |
| `LINK_LOST` | WARNING | ground | Link state LOST | Commands cannot reach the vehicle. Wait for the link; the payload stays secured | no |
| `POWER_LOW` | WARNING | ground (from Team 4) | `battery_pct` below `alerts.power_low_pct` | Consider returning to origin | no |
| `NAV_SENSOR_FAULT` | WARNING | ground (from Team 2) | Navigation `health = FAULT` | Expect position errors. Monitor the route closely | no |
| `LINK_DEGRADED` | CAUTION | ground | Link state DEGRADED | Check data ages before acting | no |
| `COMMAND_FAILED` | CAUTION | ground | A command ends FAILED | Check the reason and send the command again if still needed | no |
| `ROUTE_BLOCKED` | CAUTION | ground (from Team 2) | `nav.route_blocked` | Review the new route and arrival time | no |
| `STALE_DATA` | CAUTION | ground | Any status group older than `stale_after_s` (one alert; its title lists the stale groups) | Values marked OUT OF DATE may be wrong | no |
| `CLOCK_SKEW` | CAUTION | vehicle or ground | Timestamp more than `clock_skew_warn_s` in the future | Report to Team 1. Command timeouts may be wrong | no |

A fault clears when its condition ends. A holding fault keeps the payload HELD until it is both cleared and acknowledged. Every fault reaches the screen and Team 1 within 2 s.

## 8. Vehicle health roll-up (Status Monitor)

| Row on screen | Source | OK / WARN / FAULT rule |
|---|---|---|
| Power & Battery | Team 4 `power.status` | WARN below `alerts.power_low_pct`, FAULT at or below `alerts.power_fault_pct` |
| Mobility & Drivetrain | Team 4 `drivetrain_health` | as reported |
| Navigation Sensors | Team 2 `nav.state.health` | as reported |
| Comms Link | Team 3 `link.health` | CONNECTED = OK, DEGRADED = WARN, LOST = FAULT |
| Payload Bay Sensors | Team 5 `payload.status.sensors` | worst of the three sensors |

- **Overall:** FAULT if any row is FAULT, DEGRADED if any row is WARN or stale, NOMINAL otherwise.
- **No data yet:** a row with no data is UNKNOWN and counts as DEGRADED.

## 9. Operator Screen protocol (I1, ground process to browser)

- **Transport:** one WebSocket at `ws://localhost:8080/ws`, served by the ground process.
- **Server to browser:** a full `Snapshot` once per second, and immediately after any change. Full snapshots only, no partial patches, so the browser can never drift out of sync.
- **Browser to server:** `UiCommand` messages. Each gets one `CommandResult` straight away. After that, the command's progress shows up in `snapshot.commands`.

Copy this file exactly to `frontend/src/contracts/ui.ts`. The backend's pydantic models must produce exactly this shape. A contract test checks it (Workstream B, task B13).

```ts
// frontend/src/contracts/ui.ts : FROZEN CONTRACT (see docs/02-contracts.md)

export type Severity = "CRITICAL" | "WARNING" | "CAUTION";
export type Health = "OK" | "WARN" | "FAULT" | "UNKNOWN";
export type LinkState = "CONNECTED" | "DEGRADED" | "LOST";
export type OverallHealth = "NOMINAL" | "DEGRADED" | "FAULT";
export type PayloadState =
  | "EMPTY" | "LOADED" | "SECURED" | "TRAVELLING" | "AT_DESTINATION"
  | "RELEASED" | "DELIVERED" | "RETURNING" | "HELD";
export type MissionStatus = "QUEUED" | "ASSIGNED" | "ACTIVE" | "COMPLETE" | "ABORTED";
export type Priority = "ROUTINE" | "PRIORITY" | "URGENT";
export type CommandName =
  | "assign_mission" | "start_queued_mission" | "remove_queued_mission"
  | "abort" | "return_to_origin" | "change_destination"
  | "update_payload" | "release" | "ack_fault" | "estop";
export type CommandState = "SENT" | "RECEIVED" | "COMPLETED" | "FAILED";

export interface LatLon { lat: number; lon: number }
export interface Place extends LatLon { id: string; name: string }
export interface Dims { length: number; width: number; height: number }

/** Every status group carries its own age so the screen can mark OUT OF DATE (OI-008, OI-017). */
export interface Freshness {
  updated_at: string | null;   // the sent_at of the last message for this group, null if none yet
  age_s: number | null;        // seconds since updated_at, computed by the server
  stale: boolean;              // age_s > limits.stale_after_s, or no data yet
}

export interface LinkView extends Freshness {
  state: LinkState;
  latency_ms: number | null;
  loss_pct: number | null;
}

export interface Subsystem extends Freshness {
  key: "power" | "mobility" | "navigation" | "comms" | "payload_sensors";
  label: string;               // "Power & Battery"
  team: 2 | 3 | 4 | 5;
  status: Health;
  detail: string;              // short, ready to show: "82 % · 41 km"
}

export interface PayloadView extends Freshness {
  state: PayloadState;
  held_from: PayloadState | null;
  payload_id: string | null;
  secured: boolean;            // lock closed, sensors OK, mass in range, shift within limit
  locked: boolean;             // the lock itself
  mass_kg: number | null;
  shift_cm: number | null;
  release_energy_wh: number | null;
  sensor_health: Health;       // worst of load_cell, lock, shift
  sensors: { load_cell: Health; lock: Health; shift: Health };
  prerelease_authorized: boolean;
  departure_permitted: boolean;
  departure_reason: string | null;  // why departure is blocked, null when permitted
}

export interface NavView extends Freshness {
  origin: Place | null;
  destination: Place | null;
  position: LatLon | null;
  route: LatLon[];
  progress_pct: number | null;
  moving: boolean;
  speed_mps: number | null;
  eta_s: number | null;
  blocked: null | { reason: string; at: LatLon; old_route: LatLon[]; new_eta_s: number | null; since: string };
}

export interface Mission {
  mission_id: string;
  payload_id: string;
  status: MissionStatus;
  origin: Place;
  destination: Place;
  priority: Priority;
  declared_mass_kg: number;
  dims_cm: Dims;
  prerelease_authorized: boolean;
  created_at: string;
}

export interface CommandView {
  command_id: string;          // envelope msg_id
  command: CommandName;
  label: string;               // "Release payload"
  state: CommandState;
  reason: string | null;       // set when FAILED
  sent_at: string;
  updated_at: string;
}

export interface Permission {
  allowed: boolean;
  reason: string | null;       // why not, in plain words (OI-004)
  needs_confirmation: boolean; // OI-003
}

export interface AlertView {
  alert_id: string;            // fault_id
  code: string;
  severity: Severity;
  title: string;               // "Payload shifted 3.1 cm"
  source: string;              // "Payload" | "Team 2 Navigation" | ...
  recommended_action: string;
  raised_at: string;
  acknowledged: boolean;
  active: boolean;             // condition still present
}

export interface DeliverySummary {
  mission_id: string;
  payload_id: string;
  destination: Place;
  released_at: string;
  confirmed_at: string;
  confirm_latency_s: number;   // AEG-508 evidence
  mass_kg: number;
  energy_used_wh: number;
}

export interface Snapshot {
  kind: "snapshot";
  seq: number;                 // increases by 1 per snapshot
  server_time: string;
  test_mode: boolean;
  link: LinkView;
  vehicle_health: { overall: OverallHealth; subsystems: Subsystem[] };
  payload: PayloadView;
  nav: NavView;
  mission: {
    active: Mission | null;
    queue: Mission[];
    next_ids: { mission_id: string; payload_id: string }; // pre-filled on the form (AEG-510)
  };
  commands: CommandView[];     // newest first, at most 8
  allowed: Record<CommandName, Permission>;
  alerts: AlertView[];         // active or unacknowledged; CRITICAL first, then newest
  estop_active: boolean;
  delivery: DeliverySummary | null;  // last completed delivery (OI-016)
  places: Place[];
  limits: {
    mass_min_kg: number; mass_max_kg: number; dims_max_cm: Dims; stale_after_s: number;
    unsecured_shift_cm: number; release_energy_wh_max: number;
  };
}

export interface UiCommand {
  kind: "command";
  client_req_id: string;       // uuid from the browser
  command: CommandName;
  args: Record<string, unknown>;  // see the table below
  confirmed: boolean;          // true only after the confirmation dialog (OI-003)
}

export interface CommandResult {
  kind: "command_result";
  client_req_id: string;
  accepted: boolean;           // false = refused locally, nothing was sent
  command_id: string | null;
  reason: string | null;
}

export type ServerMessage = Snapshot | CommandResult;
```

## 10. Test interface (test_mode only)

`POST /api/test/inject` on the ground process, body `{ "target": ..., "action": ..., "params": {...} }`. The ground process publishes a `test.inject` message:
- `link` targets go to `team3.link`.
- `payload`, `nav` and `power` targets go to `vehicle.test_agent`, which calls the simulator hooks, the stand-in hooks or cancels the controller task.
- `team1` targets are handled on the ground.

`test.inject` is never delayed or dropped by the link, even during an outage, because it is test control and not mission traffic. This is how GEN-001 is met: faults are triggered from the panel or a scenario file, never by editing code.

| target | action | params |
|---|---|---|
| `payload` | `shift` | `cm` |
| `payload` | `sensor` | `sensor: "load_cell"\|"lock"\|"shift"`, `health: "OK"\|"WARN"\|"FAULT"` |
| `payload` | `mass_override` | `kg` |
| `payload` | `release_jam` | `on: bool` |
| `payload` | `controller_crash` | none. Stops the Payload Controller task to prove GEN-004 |
| `payload` | `unload` | none. The ground crew unloads a payload that came back to the origin |
| `link` | `set` | `latency_ms`, `loss_pct` |
| `link` | `outage` | `seconds` |
| `nav` | `depart`, `arrive`, `stop` | none |
| `nav` | `block_route` | `reason` |
| `nav` | `health` | `health` |
| `power` | `battery` | `pct` |
| `power` | `drivetrain` | `health` |
| `team1` | `mode` | `mode` |

Every injection is written to the Mission Log as `test.inject` so test evidence shows exactly what was triggered.
